# 00 — Решения пользователя (П1…)

**Эти правила неприкосновенны.** Любое проектирование, спецификация, план и код обязаны им соответствовать.
Если решение противоречит правилу — остановиться и спросить пользователя. Правило меняет только пользователь;
изменение записывается сюда же (старая формулировка зачёркивается, рядом — новая и дата).

Каждое решение из обсуждения записывается сюда **сразу**, в том же ответе, где оно принято.

---

## Назначение

**П1. Что делает программа** (2026-09-26).
Собирает данные из источников и выдаёт Excel-таблицу. Источники:
- Telegram-группы — люди (в первую очередь водители), упоминания о них, документы, комментарии и переписка по ним;
- сайты объявлений (olx.kz и подобные) — объявления по поисковому запросу пользователя
  («Аренда авто», «Прокат авто», «Мебель даром» и любой другой).

## Стек и архитектура

**П2. Стек** (2026-09-26). Бэкенд — Go. Фронт — React.

**П22. Интерфейс только на русском** (2026-09-26).
Все тексты интерфейса хранит и отдаёт бэкенд (как `/api/i18n` в doc-agent), чтобы другой язык можно было
добавить позже без переделки фронта. Переключателя языков в первой версии нет.

**П3. Тонкий фронт — обязателен** (2026-09-26).
Во фронте нет никакой логики: ни бизнес-правил, ни валидации, ни вычислений, ни преобразования данных.
Фронт только показывает то, что прислал бэкенд (включая подписи, ошибки, состояния кнопок), и отправляет
действия пользователя. Всё остальное — в Go.

## Таблица

**П4. Формат Excel задаётся только конструктором таблиц внутри программы** (2026-09-26).
Пользователь сам собирает колонки, их типы и порядок. Программа не подгоняется под формат
какой-либо внешней системы (taxi-saas-platform/Таксистант и др.) — ни в колонках, ни в API, ни в импорте.

**П5. Конструктор и распознавание — копия из doc-agent** (2026-09-26).
Нужные пакеты `~/doc-agent` (конструктор таблиц, Excel-экспорт, проверки значений, распознавание, клиент Ollama)
**копируются** в Пылесос и дальше развиваются независимо. Общего модуля и зависимости от doc-agent
(ни в коде, ни во время работы) нет. Исходная точка копии: doc-agent `46c6a3f` (v1.3.0-7).
Фронт конструктора пишется заново на React по П3.

**П21. «Зоны на образце» переносятся из doc-agent в первую версию** (2026-09-26).
Пользователь размечает образцы документов (удостоверение, права), где стоят опознавательные поля;
разбор читает эти места. Зоны принадлежат формам документов, а не шаблону таблицы.

## Где работает

**П10. Программа работает локально на компьютере пользователя, как doc-agent** (2026-09-26).
- ~~Один исполняемый файл для Windows/Linux/macOS~~ → один исполняемый файл для **текущей машины (Linux)**, см. П25 (2026-09-27); React-сборка встроена в Go-бинарник, окно открывается в браузере.
- Данные хранятся локально (база и файлы рядом с программой / в папке пользователя), наружу не уходят.
- Распознавание — локальная модель через Ollama на этом же компьютере.
- Бот ловит новые сообщения, только пока программа запущена. Пропуски за время простоя добирает аккаунт (П6)
  при следующем запуске: Bot API хранит непрочитанные обновления лишь ~24 часа, поэтому на него для догрузки не полагаемся.

## Telegram

**П6. История — через аккаунт пользователя, новые сообщения — через бота** (2026-09-26).
- Выгрузка истории группы: вход под аккаунтом пользователя (MTProto).
- Новые сообщения: бот (Bot API), добавленный в группу с правами админа.
- Оба пишут в одно хранилище без дублей.

**П7. Люди упоминаются свободно — программа сама их находит и склеивает** (2026-09-26).
Жёсткого формата сообщений нет: человека упоминают по имени, прикрепляют фото/скан/PDF документа,
отвечают на сообщения о нём. Модель определяет, о ком сообщение, и склеивает все упоминания одного человека;
ответы и реплики о нём — его комментарии.

**П17. Склейка людей: автоматически — только надёжное, похожее — через подтверждение** (2026-09-26).
- Автоматически склеиваются: совпадение ИИН; точное совпадение ФИО после нормализации
  (регистр, порядок слов, казахские буквы ↔ русские/латиница).
- Похожие ФИО не склеиваются сами: попадают в список «возможно, один человек», пользователь подтверждает.
- Ложная склейка двух разных людей недопустима — при сомнении не склеивать.

**П20. Люди «только из запросов» — переключатель выгрузки** (2026-09-26).
Человек без единой записи (только «есть инфо?») попадает в таблицу, только если в настройках выгрузки включено
«включать людей без записей». По умолчанию выключено; фильтрует бэкенд.

**П18. Люди общие для всех Telegram-групп** (2026-09-26).
Один человек из разных групп — одна строка; в упоминаниях видно, из какой группы запись.

## Сайты объявлений

**П11. Телефоны продавцов OLX собираются** (2026-09-26).
- Сначала телефон ищется в тексте объявления (заголовок, описание) — без обращений к сайту.
- Если в тексте нет — открывается через «Показать телефон» под аккаунтом OLX пользователя
  (вход пользователь выполняет сам в окне программы), медленно, с паузами, в пределах лимитов сайта.
- Для каких объявлений открывать телефон — переключатель в настройках **каждого** сбора:
  «все объявления» или «только отмеченные» (сначала таблица без скрытых телефонов, затем пользователь отмечает строки).
- Типовой объём одного запроса — сотни объявлений; сбор должен уметь идти часами, продолжаться после перерыва
  и не терять уже открытые телефоны.
- Капча и другие проверки на робота программой **не обходятся**: сбор ставится на паузу,
  пользователь проходит проверку сам, затем сбор продолжается.

**П13. OLX собирается через управляемый браузер и внутренний JSON API сайта** (2026-09-26).
- Программа запускает отдельное окно Chromium/Chrome со своим профилем; пользователь один раз входит в OLX сам.
- Объявления забираются постранично запросами к `/api/v1/offers/` из контекста открытой страницы olx.kz;
  телефоны — тем же запросом, что делает кнопка «Показать телефон», с паузами (П11).
- Никакого обхода защиты от ботов: без подмены отпечатков браузера, прокси, прямых HTTP-запросов в обход браузера.
- Разбор HTML-вёрстки — не основной способ (только если у площадки нет API).

## Технологии

**П14. Библиотеки и сборка** (2026-09-26).
- Telegram через аккаунт — `gotd/td` (чистый Go, MTProto). Бот — Bot API.
- База — SQLite без CGO (чистый Go). ~~…чтобы оставался один файл под Windows/Linux/macOS~~ — переносимость не цель (П25).
- Управление браузером — `chromedp`.
- Фронт — React + Vite, сборка встраивается в Go-бинарник (`embed`).

**П15. Правила кода — `.claude/rules/07-clean-code.md` и соседние файлы `.claude/rules/`** (2026-09-26).
Взяты из taxi-saas-platform и адаптированы под локальную программу; обязательны для любого кода Пылесоса.

**П16. Три независимых шага: сбор → разбор → таблица** (2026-09-26).
Сырые данные хранятся отдельно от результатов разбора, разбор — отдельно от таблицы. Каждый шаг прерывается
и продолжается с места остановки. Смена шаблона не требует повторного сбора и распознавания.
Детали — `docs/specs/2026-09-26-pylesos-design.md`.

## Данные и безопасность

**П8. Реальные персональные данные не попадают в репозиторий и документацию** (2026-09-26).
Из реальных групп в документы переносится только структура сообщений; имена, ИИН, фото — нет.
Тестовые данные — вымышленные.

**П12. Фото и сканы документов после распознавания удаляются** (2026-09-26).
- Без шифрования базы. Хранятся только извлечённые поля, распознанный текст документа и ссылка на исходное сообщение.
- Распознанный текст хранится, чтобы смена шаблона таблицы не требовала повторного распознавания.
- Если всё же нужно распознать заново — файл заново скачивается из Telegram по ссылке (через аккаунт, П6)
  и после распознавания снова удаляется.
- В Excel вместо фото — ссылка на сообщение.

**П19. Все учётные данные вводит пользователь сам, в окне программы** (2026-09-26).
Telegram `api_id`/`api_hash`, номер, код, облачный пароль, токен бота, вход в OLX. В коде и сборке
чужих или встроенных ключей нет.

## Процесс

**П9. Все решения обсуждения — сразу в документацию** (2026-09-26).
Решение → правило в этом файле; факты об источниках и чужом коде → `docs/research/`;
этапы и открытые вопросы → `docs/roadmaps/road_map.md`. Куда ещё — таблица в `CLAUDE.md`.

**П23. База знаний устроена как в taxi-saas-platform** (2026-09-26).
`CLAUDE.md` — навигатор (жёсткие правила + таблицы маршрутизации + правило обновления БЗ);
`.claude/rules/NN-*.md` — автозагружаемые правила по темам; `docs/` — контекст (`PROJECT_CONTEXT.md`,
`CURRENT_STATE.md`), `roadmaps/`, `adr/`, `reference/`, `research/`, `specs/`, `superpowers/plans/`.

**П24. Порядок этапов — по роадмапу M2 → M6, до полной готовности** (2026-09-26).
Сокращённый «сквозной срез» (быстрее к первой таблице) отвергнут. Этапы выполняются подряд,
каждый — свой план → реализация → независимое ревью → исправления.

**П25. Переносимость не нужна: программа должна работать на текущей машине пользователя (Linux)** (2026-09-27).
Сборки и проверки под Windows/macOS (`GOOS=windows/darwin go vet`) больше не обязательны; платформенный код
под другие ОС не пишется. Уже написанный (блокировка экземпляра, поиск браузера) не удаляется, но и не поддерживается.

**П26. Образец формы документа хранится в базе, пока форма не удалена** (2026-09-27).
Исключение из П12 (удалять фото документов): образец нужен для разметки зон; его загружает сам пользователь.

**П27. Цель — MVP без лишних движений** (2026-09-27).
Доводим до рабочего результата на этой машине: M4 (разбор Telegram, экран «Люди»), M5 (шаблон и выгрузка Excel),
M6 (OLX: поиск и телефоны). В MVP не входит: предложение колонок моделью, проба шаблона, импорт/экспорт шаблона
файлом, отложенные мелочи из ревью M1–M3, другие площадки (M7). Каждый этап — короткий план, реализация, одно ревью,
исправление только критичного и важного.


**П28. Итог Telegram-части — люди по документам в Excel, и всё** (2026-09-27).
Слова пользователя: «Бот должен ходить в группу телеграм или в браузере и вытаскивать людей по документам.
Заполнять поля в эксель: ФИО, ИИН и др. поля + комментарии по этому человеку, которые могут быть раскиданы в чате группы. Все.»
- Программа сама проходит группу, находит людей по документам (фото/скан/PDF) и выгружает Excel:
  опознавательные поля документа + комментарии о человеке из чата.
- Лишнего не строить: всё сверх этого — только по прямой просьбе пользователя.

**П29. Колонки Excel выбирает пользователь в конструкторе, как в doc-agent** (2026-09-27).
Подтверждение П4/П5 для итога П28: набор полей (ФИО, ИИН и любые другие из документа) пользователь собирает сам
в конструкторе таблицы; к ним — комментарии о человеке из чата. Фиксированного набора колонок нет.

**П30. OLX пока не нужен** (2026-09-27).
Этап M6 (OLX) отложен до отдельной просьбы пользователя. MVP (П27) = M4 + M5.

**П31. Выкладка на GitHub — по прямой просьбе пользователя** (2026-09-27).
Пользователь попросил залить проект в `github.com/mashbayev/pylesos`, ветка `main`. Коммит и push — только когда
пользователь просит сам (правило 7 CLAUDE.md в остальном в силе).
